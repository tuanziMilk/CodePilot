# 失败分析：从真实 trajectory 得到的改进

本文同时保留当前实验与旧目录 CodePilot 的 2026-09 调试记录。标为旧记录的样本使用旧
prompt/工具配置，不代表 `codepilot_complete` 当前版本性能。

## 2026-10-15：10 题四配置真实实验

40/40 case 通过，说明评测链路可靠，但成功率出现天花板。Lexical Retrieval 以最终修改文件为
相关项时 Hit@1=40%、Hit@3=100%；平均 read_file 从 4.3 降到 3.5。20 个 planning runs
产生 34 次 `update_plan`，其中 13 次额外调用内容完全相同。当前版本把相同 Plan 记为 no-op，
不再增加 `plan_version`，并明确提示模型继续执行或结束。该改动能修正状态与报告，但是否减少
模型轮次仍须通过 challenge suite 实测。

## 代码修复正确，但 run 仍为 max_steps

Spring `Result.success(payload)` 的源码被正确从 `code=0` 改为 `code=1`，可见测试也通过；
模型继续尝试额外命令或重复 update_plan，耗尽 12 steps，未交给 Harness 最终验证。

这说明执行预算与终止决策也影响任务成功。当前版本保留硬预算、记录 terminal state，报告不会
把“正确 diff”冒充成功。提供明确测试命令和返回码可以减少试错，但不保证模型能及时停止。

## 检索命中不等于检索收益

lexical 组首轮命中目标源码和测试，也检索出一段无关 interceptor；模型随后仍调用 list_files。
无检索组依靠任务中的 API 名也很快定位。因此单次少两步不能归因于 retrieval。

本版提供 10 个回归问题、5 个 challenge 问题和四组开关。若 full 比 basic 更慢或成功率更低，
应保留结果并分析工具拒绝、定位步骤、上下文噪声和预算，而不是不断调任务直到检索获胜。

## Basic 没强制计划，仍主动调用计划

旧实现始终提供 `update_plan`，只切换“是否必须先调用”。本版 off 模式移除工具且拒绝伪造调用，
以免把“不强制”写成“关闭 planning”的错误实验叙事。

## 工具没有输出，模型不知道退出码

旧 observation 只有 stdout 摘要。Maven 返回非零但无输出时，模型继续猜命令参数。
本版始终给出状态与退出码；UTF-8 解码使用 replacement，避免 Windows 文本解码异常造成空流。
工具层异常也记录实际已耗时，而非固定 0。

## 安全策略制造了大量参数试错

旧任务只提供 issue，模型花多步猜 `-f`、`-B`、skip-test 等参数。有些拒绝必要，有些只是能力描述
不明确。本版向所有组提供同一声明测试命令。它属于公开任务信息，会带来定位线索；正式报告
应说明这是 test-command-visible 设定，不能混用旧 command-hidden 数据计算提升率。

## 尚待正式评估的问题

- Planning/reproduction 的额外步骤是否换来更高成功率？
- 检索是否减少定位操作，还是重复已有工具读取？
- 合成任务与真实仓库的差距有多大？
- 更长任务是否因上下文累计 token 和工具预算而失败？
- 可见测试通过但额外验收不通过的比例是多少？

现阶段没有数据支持具体提升百分比。正式 Evaluation 完成后，应把可复现的结果与典型轨迹补入此文。
